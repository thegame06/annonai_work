# M1.5 — Dogfooding Report

**Annona now develops Annona.** Its own engineering knowledge lives in `annona/`,
and every task in this milestone was implemented from `annona context <task>`.

**Headline:** the workflow is usable and the context was sufficient every time.
The maintenance cost is real but small — and its shape is not what was assumed.

---

## 1. Was Annona used for real?

| | |
|---|---|
| Tasks implemented through `annona context` | 6 of 6 |
| Knowledge coverage (COMPLETE verdicts) | **100%** (6/6) |
| Contexts requiring manual supplementation | **0** |
| Mean context | 820 tokens, 13.7 nodes |
| Mean context latency | 9 ms cold, 0 ms cached |
| Cache hit ratio | 0.50 |
| Compile | 70–101 ms for 39 entities |
| Friction entries recorded | **8** |
| Tests | 46 passing |

Every number above comes from `.annona/telemetry.jsonl` via `annona metrics`, not
from recollection.

## 2. Does maintaining knowledge become a burden?

Measured rather than estimated.

| | |
|---|---|
| Knowledge base | 39 entities, 288 lines, 1,536 words |
| Code | 2,700 lines total, 348 written this milestone |
| Ratio | **1 line of knowledge per 9.4 lines of code** |
| Edits to resync knowledge after implementing | **17** |

The 17 edits are the honest number. After implementing, every task still said
`ready`, every test still said `pending`, and `touches` was wrong on 3 of 5 tasks
because the work landed in components the task never declared.

**The burden is not writing knowledge. It is resyncing status and relationships
after the work is done.** Writing the 39 entities took one pass and felt like
ordinary design work. The 17 corrections afterwards were pure overhead — mechanical,
boring, and exactly the kind of thing that gets skipped under deadline pressure.

That reframes the roadmap risk. The mitigation is not "make authoring easier"; it is
"make the after-the-fact update unnecessary or automatic."

## 3. Was the Context Compiler sufficient?

Yes, 6/6 COMPLETE, zero manual supplementation. Two efficiency observations:

- **Over-retrieval via `depends_on`.** A task touching 2 components pulled all 6,
  because component dependency chains expand transitively. Cost is roughly 300 of a
  937-token context — real but not painful.
- **Duplicated text.** `summary` and `body` both render with no overlap check,
  wasting ~40 tokens per rule.

Neither justified a change during the milestone. Both are logged with measurements.

## 4. What still requires manual work

- **Keeping `touches` honest.** Nothing connects a code change to the components a
  task declared. Only `doctor` caught it, after the fact. Real fix needs CodeIntel (M3).
- **Bugs found mid-task.** A defect surfaced while implementing something else and was
  fixed with no task at all — the workflow was bypassed to stay in flow, then recorded
  retroactively as `TASK-0006`. There is no cheap path for this.
- **Status transitions.** Every `ready → done` is a hand edit.

## 5. Defects dogfooding found

Three, all fixed, none of which the benchmark or the test suite would have caught:

1. **Term definitions never reached the runtime.** `definition` was not mapped in
   `toNode`, so all glossary entries rendered empty in every generated instruction
   file and every compiled context. The knowledge existed, was validated, and was
   silently useless. Found in the first minute of actually reading a generated file.
2. **`doctor` found 7 real gaps** in Annona's own knowledge base on first run —
   requirements with no test, components no task touches.
3. **Two requirements had no verifying test**, which `check` reports only as a warning
   and everyone would have ignored.

## 6. What shipped

| Deliverable | Status |
|---|---|
| MCP surface — 7 tools over stdio, no SDK dependency | ✅ |
| Generated instruction files — CLAUDE, AGENTS, CODEX, GEMINI | ✅ |
| Telemetry — local-only, engineering metrics, 10 permitted fields | ✅ |
| `annona doctor` — 6 read-only health checks | ✅ |
| `annona metrics` — coverage and latency from telemetry | ✅ |
| Friction log | ✅ 8 entries |

The MCP adapter takes **no SDK dependency**: MCP is JSON-RPC over stdio, and the
protocol will change faster than the knowledge format. A boundary rule enforces that
the adapter uses only the public `Workspace` API.

Instruction files are **gitignored**, per ADR-0001. One template, four filenames; a
test asserts they differ only in the preamble line.

## 7. Backlog, ordered by observed pain

Every item traces to a friction entry. Nothing here came from an architectural idea.

1. **Reduce the resync cost** (friction 7, 17 edits). Options to evaluate, cheapest
   first: infer task status from the workflow rather than storing it; a single
   `annona done <task>` that updates status and prompts for `touches`.
2. **`annona new task --from-context`** (friction 5) — a cheap path for a defect found
   mid-task, so the workflow is not bypassed.
3. **Warn when `touches` disagrees with the diff** (friction 6). Needs CodeIntel; M3.
4. **Dedupe summary/body overlap in the renderer** (friction 3). ~40 tokens per rule.
5. **Bound `depends_on` expansion** (friction 4). Measure first: ~300 tokens on a
   937-token context, which may not be worth the determinism risk of a special case.

## 8. What this cannot prove

The milestone asks for one week of daily use by engineers. This was one intensive
session by one engineer building the tool itself, which biases every result:

- **The knowledge base was authored by the person who designed the schema.** A team
  learning the model would hit friction this session cannot see.
- **100% coverage is on 6 tasks in a 39-entity project.** Coverage on a mature
  codebase with partial knowledge is the real question, and it is untested.
- **Knowledge drift over time is unmeasured.** 17 edits after one milestone says
  nothing about what happens after twenty.
- **Still no evidence that agents perform better** with the compiled context. That
  needs a model in the loop and remains the largest open question in the product.

The completion criteria are therefore **partially met**: the workflow is validated,
friction is measured, and the maintenance cost is understood in shape and order of
magnitude. The one-week criterion is not met and cannot be met in a session.
